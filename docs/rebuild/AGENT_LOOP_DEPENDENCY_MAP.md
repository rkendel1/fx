# Zig agent loop: import and dependency map

Analysis only. Nothing is deleted, disabled or changed, and this is **not** a retirement diff. It exists so that a retirement
diff, when proposed, starts from measured coupling instead of the directory name. Generated by
`docs/rebuild/tools/agent_import_map.py` on `main` at the commit this file was added; re-run it to refresh the numbers.

## Method and limits

A static scan of `@import("….zig")` path imports under `src/` (543 files). It resolves each import to a file and groups files by
directory. It does **not** see edges that exist only through comptime generics or injected context, for example
`app_agent_runtime.Runtime(Self)` in `src/main.zig`, build-graph modules, or runtime dispatch. Every figure is therefore a **lower
bound on coupling**. No named (non-path) module imports from `src/core/agent` were found, and neither `src/napi_core_main.zig` nor
`src/wasm_core_main.zig` nor `build.zig` references `core/agent` by path. This map does not by itself show that those entry points are independent
of the loop through generic parameters.

## Size

`src/core/agent` is 40 files and about 54,000 lines, of which 5 files (about 17,400 lines) are tests. Its largest files are
`runtime/orchestrator.zig` (7,765), `runtime/tests/tool_flow.zig` (6,839), `runtime/tests/gateway_flow.zig` (5,864),
`worker_runtime.zig` (5,230) and `assistant_presentation.zig` (3,421). The neighbouring `src/core/permissions` and `src/core/execution` are separate
directories with their own importers; the three together are about 72,600 lines.

## What the numbers say

* **It is not a leaf.** Fourteen areas outside `src/core/agent` import it. The heaviest users are `src/core/app` (13 files), `src/ui`
  (13), `src/core/subagent` (5) and `src/core/tooling` (4); `src/main.zig` alone imports ten agent files.
* **The entry surface is narrow.** Outside importers concentrate on a few files: `worker_runtime.zig` (24 outside importers, 5,230
  lines), `assistant_presentation.zig` (12), `question_prompt.zig` (11), `agent_runtime.zig` (9, 51 lines) and `stream_provider.zig` (9, 271
  lines). Most of the 54,000 lines have no or one outside importer. That is where a seam, if one is wanted, would go.
* **Only partly layered.** Eight areas are imported by the loop *and* import it back (`src/builtins`, `src/core/gateway`, `src/core/input`,
  `src/core/permissions`, `src/core/session`, `src/core/tooling`, `src/gateway`, `src/tools`). The loop cannot be removed without
  touching these, and they cannot be removed first without breaking the loop.
* **One-way dependents (must change with or before the loop):** `src/acp`, `src/core/app`, `src/core/cli`, `src/core/subagent`,
  `src/main.zig`, `src/ui`. The TUI and ACP being in this set is why the plan puts them last.
* **One-way dependencies (could outlive the loop):** `src/core/auth`, `background`, `config`, `execution`, `hooks`, `hosts`, `images`,
  `notifications`, `output`, `shared`, `skills`, `workspace`. Several are imported by many agent files (`shared`: 33 of 40).
* **`fx ask`.** `src/core/cli/cli_ask.zig` (9,296 lines) imports `agent_runtime.zig` and is the command front end. The parity corpus
  exercises the loop through that command. The map does not trace the call path from there.

## What this does not show

* It does not say the loop can be retired, or in what order, only where the coupling is.
* It does not cover runtime or generic coupling (see Method).
* It does not change any blocker in `retirement.json`: `zig-agent-loop` stays `blocked`.

## Candidate seam to discuss (not proposed here)

Given the concentration on five files, the lowest-risk first behavioral step would be at the command boundary
(`cli_ask.zig` choosing between the Zig loop and `chip work`), not inside `src/core/agent`. That would leave every file above in
place and be reversible by one flag. It is a behavior change with the unsupported-behaviors list attached, so it needs the review the
blocker already requires. Deleting anything under `src/core/agent` first would break the eight mutual areas.
